## Phase 2 - Foundation and sync engine
**Progress:** Phase 1 demo closed (Sprint 1.3 merged, owner test round pending his review). Sprint 2.1 (in PR): `packages/core` with UUID v7, configuration engine (single schema, layered, validated, change-reported), hash-chained audit log, No-Delete lifecycle; 10 tests; CI on three OSes (`core.yml`). **Sprint 2.2 (in PR):** permission catalogue (135 keys) with the 9 role templates, `can()` with union of roles, per-person grants and denials, branch scope, separation of duties; scrypt login with lockout; device registry (pending, approved, revoked); 23 tests. **Sprint 2.3 (in PR):** `packages/hub`: SQLite (node:sqlite, WAL, synchronous FULL) with checksum-guarded additive migrations; stock ledger (append-only, per branch/store/item/batch, no negative stock unless allowed, idempotent by key, reversal instead of delete); outbox written in the same transaction; persisted hash-chained audit; the database itself rejects UPDATE/DELETE on ledger, audit and outbox; 11 tests incl. crash atomicity and reopen. **Sprint 2.4 (in PR):** `packages/cloud` on PostgreSQL 18 with the S6 rules in the product schema (RLS enabled and forced on every table, composite keys with tenant_id, app role not superuser/BYPASSRLS/owner), per-tenant data keys (envelope encryption, bound to tenant and field), device tokens (hash only, revocable, narrow lookup function), idempotent ingest of Hub outbox events; backend framework decided: Fastify (ADR-0001); 18 tests on a real PostgreSQL. **Sprint 2.5 (in PR):** Hub to Cloud sync engine: push outbox oldest first in batches, remove an event only after the Cloud acknowledges its id, pull other branches' events with a cursor stored together with the events, own events never come back, offline never blocks local work, exponential backoff with jitter, sync status for staff; Cloud `GET /v1/pull`, per-tenant ingest lock so the cursor can never skip an event; tested against a real PostgreSQL with two branches of one tenant, lost acknowledgements, restart from a file database, concurrent pushes and a 25%-loss fault storm (converges exactly: 90 events stored once, 60 and 30 received once). **Decision:** the Hub's local API for devices (POS, phones, tablets on the shop network) is built with the first real screens (Phases 3-4), because its contract depends on them; the Hub core it will call is ready. **Sprint 2.6 (in PR, first half):** licences (Ed25519-signed; valid, grace, then read-only: a pharmacy is never locked out mid-day and data stays readable and exportable; single edition one branch, chain-only features need the chain licence) and the auto-update engine (signed manifest, SHA-256 check, never downgrade, staged rollout stable per device, install outside business hours, forced below the minimum version, rollback after repeated failed starts); 34 core tests. Desktop shell decided provisionally: Electron as a thin window over the separate Hub service (ADR-0002, owner may veto). **Still to do in this phase:** installer per OS, service registration and update install/rollback proven on real Windows and macOS machines (needs the owner's PC and a Mac or CI runners; proposed as Sprint 2.7). CI runs the cloud tests on Linux and macOS (embedded Postgres refuses to run as admin on the Windows runner, as in S6).
Identity, role templates with multiple roles per person (D23), permissions, devices, branches/stores, configuration, audit, licensing/editions, Hub ↔ Cloud sync, installer and auto-update, cloud tenancy with RLS and per-tenant keys (D25). ## Phase 3 - Master data, inventory, purchasing
**Progress:** Sprint 3.1 (in PR): `packages/inventory` - item master (drug / non-drug / service), units with whole conversion factors that never change (a new unit is added instead), several barcodes per item and unit with GTIN check digits, GS1 Data Matrix parsing (GTIN, batch, expiry, serial) on scan, ETA item code (GS1 or EGS) and taxable/exempt flag on every item, drug price never set on the item (D14) and free non-drug price behind `item.price.set` (D20), Arabic-aware search (alef, ya, ta marbuta, diacritics, Arabic digits), alternatives by ingredient/strength/form, suspend / archive / restore with reason and full log (D13), groups; every change writes ledger-grade audit and an outbox event in one transaction; database triggers back No-Delete; 23 tests; 25,000 items: about 7 ms per search or scan. Module owns its tables (migration `inv_0001_items` plugs into the Hub). **Sprint 3.2 (in PR):** batches (lot, expiry, cost, state public and pharmacist price per batch; migration `inv_0002_batches`): receive creates the batch and the stock movement together (same lot and expiry with the same prices adds to it, other prices are refused for management to resolve; repeated delivery adds nothing); a drug batch must carry the state public price and pharmacist price cannot exceed it (database trigger too); non-drug prices stay on the item (D20); expired batches cannot be received; prices, lot, expiry and cost never change after receipt (database trigger); FEFO allocation (nearest expiry first, expired and quarantined never sold, each pick at its own batch price so old and new prices sell side by side, optional chosen batch, shortage reported not invented); stock per batch comes straight from the ledger; expiry report (window, nearest first, value at cost only for those who may see cost); quarantine / release for recalls with reason and log; cost hidden from Pharmacist and Cashier; month/year expiry means end of month; money in whole piasters, rounded half up once per pick; 41 inventory tests. **Sprint 3.3 (in PR):** stores and stock views (migration `inv_0003_stores` plus hub migration 0005 for item-first lookups): a main store from day one, more stores (back store, returns, expired, quarantine) created and switched off (only when empty, never deleted), a store flagged not-sellable is never sold from; transfers between stores follow FEFO across batches, are all-or-nothing and safe to repeat (same key = same transfer number), logged with audit and outbox; stock card (kardex) with opening balance, running balance, date range, store filter, lot shown only with batch view; stock summary (total vs sellable, expired and held excluded) in one query; valuation at cost per batch with expired value apart (cost view only); low-stock list against the reorder level; 53 inventory tests. 75,000 movements across 25,000 items: summary 81 ms, stock card 0.1 ms. **Sprint 3.4 (in PR):** stock adjustments and stocktake (migration `inv_0004_stocktake`): an adjustment is a request (reason code and note required, never more out than the store holds) that changes nothing until someone else approves (separation of duties; one-person pharmacy allowed but flagged), then one ledger movement; rejected with a reason; stocktake of one store (all items or chosen ones, one open per store): snapshot, blind count (counters do not see the system quantity), the system quantity is taken at the moment each line is counted so sales during the count do not distort the variance, found stock can be counted, submit, review (shortage and overage units, net value at cost for cost viewers, uncounted lines), send back for recount, approve and apply all-or-nothing as ledger adjustments, uncounted lines untouched, cancel with reason; nothing deleted (triggers); 63 inventory tests. **Sprint 3.5 (in PR):** purchasing (migration `inv_0005_purchasing`): suppliers (never deleted, switched off with a reason); purchase orders (draft, sent, partly received, received from the invoices that name them, cancel with reason); supplier invoices posted in one transaction (each line creates or tops up a batch and its ledger movement, any bad line stops the whole invoice, repeated key changes nothing, the same supplier invoice number cannot be entered twice, near-expiry and cost-above-price warnings by line); bonus quantity adds free stock and lowers the effective cost; void by someone else, refused once the stock is sold (return it to the supplier instead); returns to supplier (batch, quantity, reason, valued at batch cost, never below zero); supplier price comparison (last effective cost per supplier, cheapest first); 74 inventory tests. **Sprint 3.6 (in PR):** import from eStock (migration `inv_0006_import`, permission `item.import`): CSV files (comma, semicolon or tab; quotes; Arabic digits and decimal comma) for items, opening stock and suppliers; the usual Arabic eStock headers are mapped and unknown columns are reported; dry run first (writes nothing), then apply `all_or_nothing` (default) or `valid_only`; every problem comes back with its file line number; same file twice = same import (no double stock); existing items skipped (or refused on request); eStock item codes are kept as references so later files find the items; groups created on the fly; a drug price in the file is ignored (state price comes per batch, D14) and a drug stock row without the state public price is refused; opening stock is written as `opening` movements per batch; expired lots go to an expired store and are never sold; import history is append-only; 3,000 items in 1.2 s and 3,000 batches in 1.9 s; 87 inventory tests. **Phase 3 complete.** The real eStock column names still need one sample file from the owner (owner-actions item 11). Next: Phase 4 (POS, printing, e-receipt), first sprint 4.1 cashier sessions and the sale core.

## Phase 4 - POS, printing, e-receipt
Cashier sessions, all sale types, FEFO batch selection (D21), returns and swaps, held bills, customer balances, receipts and labels, drawer closing, ETA e-receipt adapter (D26).
**Progress:** Sprint 4.1 (in PR): `packages/pos` (migration `pos_0001_sales`, plugs into the Hub after inventory): cashier sessions (one open per terminal and per person, opening float, close with counted cash: the cashier counts blind, reviewers with `drawer.close.review` see expected and difference, a difference needs a note); cash sale in one transaction (nearest expiry first, each batch at its own price, money in whole piasters rounded half up once per batch pick, change, batch spread over several stores drawn from each, chosen batch honoured, held/expired/returns-store stock never sold, non-drug at the item price, services take no stock, pharmacist price needs `sale.discount`, negative stock only for non-drugs when configured, repeated key sells nothing twice, refusals leave no trace); void by management with a reason while the session is open (reverses every movement, never deleted; after close a return is the way, Sprint 4.3); cost and profit per sale only for cost viewers; view own / view all; 13 POS tests. **Sprint 4.2 (in PR):** migration `pos_0002`: payments (cash, card with approval reference, mixed with change; the drawer expects cash only), discounts (basis points per line or per sale, rounded half up per batch pick, `sale.discount` needed, above config `sale.cashierDiscountMaxPct` needs `sale.discount.override`), held bills (park a basket without touching stock, resume then sell, cancel with reason, the session cannot close while one is open), home delivery (customer details and fee, the unpaid part is cash on delivery, out for delivery with the agent, collected into the collector's open session, a failed delivery voids the sale and returns the stock; after the session closes it becomes a return, Sprint 4.3); session summary now shows cash, card and cash still owed on delivery; 23 POS tests. Credit sales move to 4.4 with customers and balances (they need a customer and a credit limit). **Sprint 4.3 (in PR):** migration `pos_0003`: returns from a sale (`sale.return`): goods go back to the batch they were sold from (resellable to the main store, damaged to a returns store and never sold), refund is the exact net price paid (discount included; partial returns add up to the total with no rounding drift), cannot return more than was sold, cash comes out of the drawer or goes back to the card (only up to what was paid by card, with the reference), reason required, works after the session closed (the refund comes from the returner's open session); swap (`sale.swap`): the refund value is credit against the new sale, the customer pays the difference or gets it back, the returned goods are on the shelf first so the swap can sell the batch that just came back; void is refused once anything was returned; an unfinished delivery cannot be returned (mark it failed); everything append-only; 33 POS tests. Next: 4.4 customers, credit sales and balances.

## Effort estimates v1.1 [ESTIMATE, plus or minus 50 percent, no commitment]
Pace assumed: Claude builds, the owner reviews in short rounds (phase gate), no other developers. Months of elapsed work; they move with how fast decisions and test rounds come back.

| Phase | Months | Main uncertainty |
|---|---|---|
| 1 Demo | 1-2 | Owner's change list after testing |
| 2 Foundation and sync | 3-4 | Auto-update, desktop shell choice, Hub on three OSes |
| 3 Master data, inventory, purchasing | 3-4 | eStock import quality, batch and price rules |
| 4 POS, printing, e-receipt | 3-4 | Real printers, ETA offline rules and approved-provider route |
| 5 Operations (YK base) | 3 | Porting YK logic onto native stock |
| 6 Accounts, HR/payroll, contracts, reports | 3-4 | Size of the report centre |
| 7 Pilot (one full month of closed days minimum) | 1-2 | Findings in the pilot month |
| 8 Chain edition | 3 | Cross-branch rules (D15-D22) |
| 9 Customer App and Website | 2-3 | Per-pharmacy build pipeline |
| 10 Compliance depth | 2 | EDA pharmacy duties still unpublished |
| 11 Commercial launch | 2-3 | Penetration test, signing, onboarding |

**Totals:** Phases 1 to 7 (the pilot done): about **17 to 23 months**; all phases: about **26 to 34 months**.

**Option for the owner (decision D-P7):** run the pilot earlier, side by side with eStock, right after Phase 4 (sell, stock, buy, print) while Operations and Accounts are built after it. This puts real use about **10 to 14 months** out and lets the pharmacy find problems sooner, at the cost of two-system work for the staff during that time. Phase 7's exit rule stays the same.

## Cross-cutting (every phase)
Tests green in CI, security review, backups verified, in-app guide/handbook updated, no new permission/module without approval, documents updated in the same PR.

## Ordering principles
Retire the biggest risks first (offline/sync, the Hub on three platforms, printing, tenant isolation, compliance) in Phase 0. Build the Chain-ready data model from Phase 2 although the Chain edition ships in Phase 8. Anything that touches money or stock is a ledger with audit.
